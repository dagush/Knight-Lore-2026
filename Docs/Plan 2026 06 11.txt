Knight Lore 2026 full 3D plan - 2026-06-11
==========================================

Purpose
-------
This plan starts the final large stage of the project: moving from the verified
schematic semantic renderer to a real "Full 3D" renderer.

Stages 0..5 have established the important foundation:
- the emulator/game logic remains untouched;
- semantic working memory is captured frame by frame;
- static room/background data is available;
- the schematic Three.js view renders rooms, walls, arches, portcullises,
  fixed backgrounds, dynamic objects, charms/items, the player proxy, the
  wizard/mage, spell/bubbles, cauldron, and the ending screen;
- the Spectrum framebuffer remains the visual ground truth for validation.

This next stage must not throw away that validation work. The "Schematic" view
should remain as the strict debug/reference view while "Full 3D" becomes the
target presentation view.

Core rule
---------
Do not replace data-driven semantic rendering with hand-placed art.

Full 3D should use the same decoded room/background/object/player records as
Schematic mode. Assets, textures, and nicer geometry may improve appearance,
but they must not become a second independent game description.

High-level sequence
-------------------
1. Add the real Full 3D mode switch.
2. Build a Full 3D renderer scaffold using the same scene data as Schematic.
3. Fix proportions and pivot conventions for the shared template objects.
4. Replace doors/arches first, preferably using Ricard's 2006 assets if they
   can be recovered cleanly.
5. Recover wall texture extraction/dewarping.
6. Apply the same texture method to tree rooms.
7. Create or import 3D models for simple static/simple dynamic objects.
8. Solve animated/dynamic object families with conservative visual rules.
9. Validate room by room against the emulator and Schematic view.
10. Only then consider polish, lighting, camera, and hiding debug surfaces.

Stage 6.0 - Asset inventory and import decision
-----------------------------------------------

Goal:
Know what original or 2006-era assets are actually available before designing
the final asset pipeline around them.

Tasks:
- Locate Ricard's 2006 3D assets:
  - arched doors;
  - wall/door/tree texture assets, if any;
  - object models, if any;
  - source formats and exported formats.
- Record their location, format, units, orientation, and licensing/provenance in
  a short asset inventory section or file.
- Check whether the repo should store these assets directly or whether they
  should live in a separate source/art folder.
- Test one asset load path in isolation:
  - GLTF/GLB if available;
  - OBJ/MTL if that is what exists;
  - converted GLTF if the original format is old or awkward.

Recommendation:
- Prefer GLTF/GLB as the runtime format even if the recovered originals are
  OBJ/3DS/Blend/etc.
- Keep originals in a clearly named source-assets folder and use generated
  runtime assets separately if conversion is needed.

Exit criteria:
- We know whether Ricard's assets are available.
- We know the import/conversion path.
- One test asset can be loaded in Three.js without affecting the emulator.

Strict doubts:
- The assets were not found in the repo during planning.
- If the assets are not immediately available, do not block Full 3D entirely:
  use temporary local geometry for the first Full 3D scaffolding, then swap in
  recovered assets later.

Initial inspection result:
- The recovered 2006 folder is `Docs/KL 2006`.
- `main.c` contains the relevant arches, blocks, player proxy, and simple
  object models as procedural OpenGL/GLUT commands.
- The many small `*_*.c` files are texture-wall data emitted as C arrays and
  should remain out of this pass. They belong to the later wall texture and
  dewarping stage.
- The arch is not an external mesh. It is generated by `dibujar_arco()` as
  repeated calls to `ladrillo_arco()`, which draws a small prism/brick.
- Many simple objects are similarly procedural:
  - blocks reuse the same brick/prism helper;
  - spikes use cones;
  - balls and spike balls use spheres;
  - fire uses two small coloured spheres;
  - the old player proxy uses two spheres plus a cone pointer.
- The 2006 coordinate convention is useful:
  - room floor is approximately 8 x 8 OpenGL units;
  - object height uses `pz * 0.75`;
  - this maps cleanly to the current 64-unit room box by using an 8x scale
    factor, because `0.75 * 8 = 6`, matching the current 12-pixel-to-6-unit
    vertical mapping.

Decision:
- Do not export these simple procedural objects to standalone mesh files yet.
- Translate the OpenGL recipes into Three.js object-builder functions.
- Keep the translated builders parametric and data-driven, so they can be
  placed by the existing semantic records rather than by fixed room-specific
  coordinates.

Recommended code structure:
- Add a dedicated runtime module rather than growing `semantic3d.js` further.
- Prefer a specific name such as `runtime/knightlore-full3d-objects.js` or
  `runtime/knightlore-objects3d.js` over a generic `objects.js`.
- The module should export builders such as:
  - `createArchModel(options)`;
  - `createBrickPrismModel(options)`;
  - `createSimpleObjectModel(spriteId, options)`;
  - later, `createPlayerModel(state, options)`.
- `semantic3d.js` should remain responsible for semantic placement and mode
  switching; the new module should only create reusable Three.js geometry/groups.

Stage 6.1 - Full 3D mode scaffold
---------------------------------

Goal:
Make the existing "Full 3D" button a real mode beside "Schematic" without
changing the data path.

Tasks:
- Enable the existing render-mode toggle:
  - Schematic;
  - Full 3D.
- Keep one Three.js scene/camera if practical, but separate render layers or
  groups clearly:
  - schematic room/background/object groups;
  - full 3D room/background/object groups.
- Full 3D mode initially may show the same simple geometry as Schematic, but
  it must be independently switchable.
- Keep diagnostics and raw semantic state unchanged.
- Do not remove Schematic mode.

Verification:
- Switching modes does not reload the emulator.
- Switching modes does not reset game state.
- The current room, player, items, spell, and dynamic objects stay synchronized
  after repeated mode switches.
- The original Spectrum view still works.

Exit criteria:
- Full 3D mode exists and is active through the UI.
- Schematic remains the default validation view or at least remains available.

Strict recommendation:
- Keep Schematic as the "truth/debug" renderer even after Full 3D becomes the
  attractive view. It is too valuable for regression checking to remove.

Stage 6.2 - Full 3D template object proportions
-----------------------------------------------

Goal:
Before importing many assets, establish consistent units, pivots, and bounding
boxes for all common Full 3D object templates.

Objects to normalize:
- room floor and walls;
- wall thickness;
- arch/door opening;
- portcullis/reja;
- tree wall/filler;
- generic block;
- movable block;
- disappearing/collapsing block;
- table;
- rock;
- chest;
- spikes/spike block;
- spike ball;
- cauldron;
- wizard/mage body/head placeholders;
- spell/bubble marker;
- player human/wolf proxy.

Tasks:
- Define a template object registry keyed by semantic class and/or sprite id.
- Give each template:
  - nominal width/depth/height in current room units;
  - pivot point;
  - local forward direction;
  - collision/visual origin relation;
  - schematic fallback.
- Replace ad hoc size choices with template dimensions where the semantic class
  is known.
- Keep unknown dynamic records as wireframe/full-colour fallback boxes.

Verification:
- Existing schematic alignment is not broken.
- Full 3D mode immediately looks closer to the Spectrum room proportions even
  before real textures are added.
- Doors, player, blocks, tables, and common objects feel plausible in relative
  scale.

Exit criteria:
- A room with doors, player, blocks, and at least one live item can be viewed in
  Full 3D with coherent proportions.

Strict doubts:
- The exact object dimensions encoded by Knight Lore's visual records may not
  always map directly to visually pleasing 3D meshes.
- Recommendation: use decoded dimensions as placement/bounds, but allow
  per-class visual scale factors as long as the object remains inside its
  decoded footprint.

Stage 6.3 - Arched doors and portcullises first
-----------------------------------------------

Goal:
Replace the schematic arch/door geometry with real Full 3D door assets or
well-proportioned procedural models.

Why first:
- Arched doors define the room silhouette.
- Door/arch alignment is already well decoded.
- Errors are easy to see against the emulator.
- Ricard's 2006 assets likely targeted these elements.

Tasks:
- Map background ids to door classes:
  - arches: `0x00..0x03`;
  - tree arches: `0x04..0x07`;
  - portcullises/rejas: `0x08..0x0B`;
  - high arches/bases if needed: `0x14..0x17`.
- Create a Full 3D arch placement adapter:
  - choose side;
  - position in room;
  - rotate to side;
  - scale to current room size/opening convention.
- Import Ricard's arch asset if available.
- If not available, create a temporary procedural arch:
  - two side pillars;
  - top arch or curved/stepped lintel;
  - optional thickness.
- Replace portcullises with a clearer barred 3D object:
  - frame;
  - vertical bars;
  - optional depth.

Verification:
- Several rooms show the same arch side/opening pattern as the emulator.
- Door assets do not float, sink, or face the wrong direction.
- Full 3D and Schematic agree on which openings exist.

Exit criteria:
- Full 3D arches and portcullises are visually useful in all four directions.

Strict doubts:
- If Ricard's assets have a different coordinate system, do not force the whole
  renderer to match them. Add an asset-normalization wrapper.

Stage 6.4 - Wall texture extraction and dewarping
------------------------------------------------

Goal:
Recover the 2006 technique for turning original wall/background sprites into
correct 3D wall textures.

Analysis tasks:
- Re-read chapter 5's wall-texture/dewarping description before coding.
- Identify the original source sprite data used for wall textures:
  - sprite pointer table around `0x7112`, if needed;
  - sprite data range around `0x728A..0xAF6B`;
  - background ids and expanded background records.
- Identify the exact wall image/sprite variants used by:
  - wall presets `0x0C`, `0x0D`, `0x0E`;
  - tree room preset `0x0F`;
  - tree fillers `0x10`, `0x11`;
  - arches and portcullises if they use sprite-derived texture pieces.
- Recover or reimplement the 2006 dewarp mapping:
  - original isometric/projected wall pixels;
  - target rectangular wall plane texture;
  - transparency/masks;
  - palette/attribute handling.

Implementation tasks:
- Build a small offline or runtime texture extractor:
  - input: decoded sprite/background data;
  - output: canvas/texture image;
  - debug output: visible PNG/canvas preview.
- Generate wall textures independent of gameplay frames when possible.
- Apply textures only in Full 3D mode.
- Keep Schematic debug colours available.

Verification:
- Side-by-side compare:
  - original emulator room;
  - extracted/dewarped texture preview;
  - Full 3D textured wall.
- Test at least:
  - normal stone room;
  - room with two doors;
  - rectangular room;
  - room with portcullis.

Exit criteria:
- Stone/wall rooms have stable textured walls in Full 3D mode.
- Texture placement can be explained from decoded static/background data.

Strict doubts:
- This is one of the highest-risk stages. Texture dewarping may require more
  historical detail from the 2006 implementation than we currently have.
- Recommendation: first make a standalone texture preview/debug panel, then
  attach textures to the 3D scene after the mapping is verified.

Stage 6.5 - Tree rooms and tree walls
-------------------------------------

Goal:
Apply the same Full 3D texture/model approach to tree rooms.

Tasks:
- Treat tree backgrounds separately from stone walls:
  - tree room preset `0x0F`;
  - tree filler west `0x10`;
  - tree filler north `0x11`;
  - tree arches `0x04..0x07`.
- Decide whether tree walls are best represented as:
  - textured flat wall planes;
  - slightly thick/irregular wall meshes;
  - repeated trunk/branch modules.
- Start conservative:
  - textured planes or low-relief geometry;
  - same placement path as existing tree-room schematic.
- Add tree arch variant using the same arch placement adapter.

Verification:
- Navigate to known tree rooms.
- Confirm Full 3D tree walls match side and filler placement from Schematic.
- Confirm doors/arches still align in tree rooms.

Exit criteria:
- Tree rooms no longer look like recoloured stone rooms in Full 3D mode.

Strict recommendation:
- Do tree rooms after stone wall texture dewarping, not before. They are likely
  to share the same extraction/mapping problem but with more visual ambiguity.

Stage 6.6 - Simple object models
--------------------------------

Goal:
Replace generic wireframe/dumb boxes with recognizable Full 3D models for
static and simple dynamic objects.

Object families:
- fixed blocks;
- movable blocks;
- moving blocks;
- disappearing/collapsing blocks;
- rocks;
- tables;
- chests;
- spike blocks;
- spike balls;
- cauldron;
- charms/items.

Tasks:
- Build or import low-poly/simple models for each family.
- Map object templates from working-memory sprite/object ids to model families.
- Use decoded dynamic record position and dimensions for placement.
- Keep unknown objects as wireframe fallback boxes.
- For charms/items:
  - keep the live two-slot logic;
  - use small distinguishable item markers or charm-specific proxies;
  - do not return to the storage table as the live source.

Verification:
- Rooms with blocks/tables/rocks look recognizable without breaking alignment.
- Moving/movable objects still update frame by frame.
- Picked-up charms disappear when their live slot is inactive.

Exit criteria:
- The most common non-character objects no longer rely on generic wireframes in
  Full 3D mode.

Strict doubts:
- Some sprite ids may be visually different but behaviourally equivalent.
- Recommendation: group by practical visual family first, then split into more
  detailed variants only when the emulator comparison justifies it.

Stage 6.7 - Main character Full 3D proxy upgrade
------------------------------------------------

Goal:
Improve the player representation without losing the verified orientation and
state logic.

Tasks:
- Keep the existing proven state/orientation classifier:
  - human/wolf from body sprite;
  - direction from body sprite plus `0x5C0F` axis threshold;
  - orientation updates every semantic frame.
- Replace box/head/cone proxy in Full 3D mode with:
  - a simple humanoid/wolf proxy;
  - or two low-poly state-specific models;
  - still using the cone or a subtle direction marker during validation if
    needed.
- Keep Schematic mode unchanged for debugging.
- Match player model footprint to decoded body position and room units.

Verification:
- Human and wolf orientation still match north/south/east/west.
- Transformation does not break direction.
- Room transitions and menus still hide the player correctly.

Exit criteria:
- Full 3D player looks closer to a character while preserving the validated
  semantic orientation.

Strict recommendation:
- Do not introduce animation before the static orientation/model placement is
  correct.

Stage 6.8 - Animated and hazardous object families
--------------------------------------------------

Goal:
Create practical Full 3D representations for dynamic entities whose sprites
change over time.

Object families to solve:
- ghosts;
- guards;
- spells/bubbles;
- cauldron spell/attack state;
- fires;
- bouncing balls;
- spike balls;
- other hazards found during gameplay.

Tasks:
- Use the existing dynamic working-memory slot stream as source of truth.
- Map sprite-id ranges to visual families.
- For each family define:
  - base model;
  - sprite-state to material/model variant;
  - optional simple animation effect;
  - fallback for unknown sprite id.
- Treat special effects conservatively:
  - spells/bubbles can be spheres/particles;
  - fire can be small animated billboards or simple emissive geometry;
  - ghosts/guards can be low-poly placeholders or sprite billboards initially.

Verification:
- Dynamic entities move exactly with decoded working-memory records.
- Sprite cycling changes appearance without changing gameplay interpretation.
- No Three.js-side physics is introduced for gameplay objects.

Exit criteria:
- The common hazardous/moving entities are visually identifiable in Full 3D
  mode.

Strict doubts:
- Faithful modelling of every animated sprite may be expensive.
- Recommendation: for early Full 3D, prefer identifiable low-poly models or
  billboard/sprite hybrids over over-detailed models.

Stage 6.9 - Texture/material system and palette policy
------------------------------------------------------

Goal:
Make Full 3D visual styling consistent without losing the Spectrum origin.

Tasks:
- Define a material registry:
  - stone walls;
  - tree walls;
  - floors;
  - arches;
  - blocks;
  - metal bars/spikes;
  - player human/wolf;
  - magical effects;
  - items/charms.
- Decide when to use:
  - extracted Spectrum textures;
  - generated textures;
  - flat low-poly colours;
  - billboard sprites.
- Keep room colour from semantic `0x5BAD` for room material tint if still
  useful.
- Do not use Spectrum post-processing screen writes as semantic 3D colour.

Verification:
- Full 3D is not dominated by one colour family.
- Stone rooms, tree rooms, and special rooms are visually distinguishable.
- Materials remain readable at the current orthographic camera distance.

Exit criteria:
- Full 3D has a coherent visual style and does not look like debug geometry with
  random colours.

Strict recommendation:
- Avoid chasing the cauldron colour-cycling post-process in this stage. It is a
  screen-memory effect, not semantic room state.

Stage 6.10 - Validation matrix and regression route
---------------------------------------------------

Goal:
Make sure the Full 3D renderer is correct across the game, not just in one or
two favourite rooms.

Build a manual validation route:
- square stone room;
- rectangular room in X;
- rectangular room in Y;
- room with multiple arches;
- room with portcullis;
- tree room;
- room with blocks/tables/rocks;
- room with moving hazards;
- room with charm pickup/drop/push;
- cauldron room `0x88`;
- ending screen.

For each room check:
- Spectrum view still works.
- Schematic view still matches the semantic data.
- Full 3D matches Schematic placement.
- Full 3D visually resembles the emulator.
- Player orientation remains correct.
- Dynamic objects update without lag or starvation.

Possible automated checks:
- browser smoke test loads workbench with no console errors;
- Full 3D mode can be toggled;
- WebGL canvas is nonblank;
- semantic frame counter advances;
- emulator regression test still passes.

Exit criteria:
- Full 3D can be used for normal gameplay comparison without needing the
  schematic view for every room.

Stage 6.11 - Performance and switch-over polish
-----------------------------------------------

Goal:
Make Full 3D pleasant and stable enough for continued development.

Tasks:
- Avoid rebuilding static meshes every frame.
- Cache static room meshes by room id/background signature where safe.
- Keep dynamic objects updated by transforms/material changes rather than full
  geometry recreation where practical.
- Dispose unused geometries/materials/textures correctly.
- Check emulator responsiveness with Full 3D enabled.
- Decide whether Full 3D should eventually become the default mode.

Verification:
- Emulator controls remain responsive.
- Room transitions do not leak obvious memory or accumulate stale objects.
- Full 3D mode can run for a sustained gameplay session.

Exit criteria:
- Full 3D is stable enough to become the primary development view, while
  Schematic remains available for strict diagnostics.

Strict final recommendation
---------------------------
The safest route is:
1. Full 3D mode switch.
2. Template proportions and pivots.
3. Arches/doors.
4. Stone wall textures/dewarping.
5. Tree rooms.
6. Common object models.
7. Player proxy upgrade.
8. Animated/hazard families.
9. Full validation route.
10. Performance/polish.

Do not start by modelling every object or extracting every texture. The visual
renderer will converge faster if each pass has one clear comparison target and
one clear rollback path to Schematic mode.

Open decisions before implementation
------------------------------------
- Where exactly are Ricard's 2006 assets, and what format are they in?
- Should recovered original/source assets be committed to this repo, or kept in
  a separate art/source folder with generated runtime assets committed here?
- Should the first Full 3D arch use Ricard's asset, if available, or a temporary
  procedural arch while the import pipeline is stabilized?
- Should wall texture dewarping be implemented as an offline generator, a debug
  in-browser generator, or a runtime-on-demand generator?

Recommendation for these decisions:
- Use a procedural placeholder if asset recovery blocks the first Full 3D mode.
- Use GLTF/GLB for runtime model assets.
- Build texture extraction first as a visible debug/preview tool, then use its
  output in Full 3D after validation.
- Keep all semantic placement driven by the already-verified working-memory and
  static-background decoders.
